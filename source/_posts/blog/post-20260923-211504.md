## Patch 制作与提交
> 目前主要都靠 Agent 进行 Patch的生成，但一般 Agent 不会知道制作 Patch 需要注意检查哪些格式，哪些内容，有的流程比较固定可以作为 skill，这里就是记录一下注意点，方便后续设计 skill
### 投递之前的一些检查点
1. 上游是否已经修复，其实最好直接扫描最新的内核，检查上游往往是扫描的内核和目前主线版本隔得比较远
2. 如果修复方式不确认，可以打 RFC 标签，或者发邮件询问
3. Fixes 标签的内容是否准确，是否是 upstream commit
4. 是否有必要加 cc: stable，如果修复的问题比较弱，可能没必要
5. 一些子系统需要注意格式还有投递要求，比如：net
6. commit message 要简练清楚，不要有一些影响reviewer审阅的无关信息
7. 用 LLM 生成 Patch 需要打标签：  Assisted-by: LLM
8. checkpatch 脚本 getmaintianer脚本
### Patch的回复
1. 如果收到 appllied 那就是 patch 被接收合入了，就不用回复了
2. 如果有 reviewer 的反馈，先看 reviewer是否有提问，然后针对提问给出回答，最好是写本地邮件然后指令发送回复
3. 制作新版本要加 v2 v3 等等，发送的时候最好通过 Message-Id 接着前面的邮件
4. 一些子系统像 net 需要间隔 24h 才能投递新版本，并且每一版 Patch 都要开一个新的主线，每天和每周的投递数量也是有限制的
5. 如果确定修复有误需要撤回要单独发邮件
